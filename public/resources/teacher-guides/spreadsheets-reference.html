REFERENCEFacilitator data infrastructure

Spreadsheets that power Velocity Arena.

Five distinct Google Sheets integrations move data between students, facilitators, and the dashboard. This page lists every file that writes to or reads from a Google Sheet, what each one needs from the facilitator, and where to look when something stops working. One file rules them all: config.js — every endpoint URL lives there.

01 Student lesson submissions. 1 shared sheet

Six lesson pages POST student work to the same Apps Script web app (AKfycbzV0_UPT…). Every student response across these six lessons lands in one shared spreadsheet, one row per submission.

File What it writes
lessons/speed-stat.html (+ es/) Day 1 Speed-stat lesson answers
lessons/endurance-stat.html (+ es/) Day 2 Endurance-stat lesson answers
lessons/endurance-discovery.html (+ es/) Day 2 Endurance discovery responses
lessons/power.html (+ es/) Day 4 Power lesson answers
lessons/power-stat-challenge.html (+ es/) Day 4 Power-challenge answers
lessons/prove-your-build.html (+ es/) Day 5 Prove-Your-Build commitment
Facilitator action Open the shared lesson-submissions spreadsheet to see who completed which lesson, with what answers. One sheet is the source of truth across all six lessons. If a row is missing, check the student's browser console — the form will console.error on failure.
02 Live Dashboard + Leaderboard. Per-site sheet

The match dashboard and leaderboard route to different spreadsheets per pilot site. Each site has its own Apps Script web app that writes to its own sheet, keyed by the cohortTag in the URL.

File Sites it routes to
activities/dashboard/velocity-arena-dashboard.html Tennessee · NYC1 (Gotham Tech) · NYC2 (Claremont) · NYC3 (South Bronx)
activities/dashboard/leaderboard.html Tennessee (reads from the same per-site routing)
Facilitator action Match data lands in the per-site sheet matched by the cohortTag. If your site shows empty data, three things to check: (1) the right cohortTag is in the URL, (2) the site's Apps Script web app is deployed and redeployed after any code changes, (3) the URL in config.js matches the deployed web app's /exec endpoint exactly.
03 Pre-Task Diagnostic (Day 1). Per-state sheet

Each state pilot site (MI, NY, RI, TN) has its own diagnostic spreadsheet. The student-facing diagnostic page writes through a service account (not via Apps Script), and the growth dashboard reads from those sheets to produce the per-concept comparison.

File Purpose
activities/diagnostic/SETUP.md The setup walkthrough. Step-by-step instructions for creating a state-specific Google Sheet, a Google Cloud service account, and connecting them. ~15-minute one-time setup per state.
activities/diagnostic/index.html Where students take the Day 1 pre-task — writes through the service account
activities/diagnostic-post/index.html Where students take the Day 15 post-task — same sheet, marked "post"
activities/diagnostic-dashboard/index.html Anonymized per-concept growth comparison, pre vs. post
Facilitator action Every state pilot needs its own sheet configured per SETUP.md before Day 1. Without it, the diagnostic UI submits but no row lands anywhere — you'll lose your baseline. The Day 15 post-task uses the same sheet; the dashboard only shows growth when both rows exist for the same student.
04 What-If Loadout Analysis. 1 sheet · CSV + Apps Script

The Week 3 What-If analysis reads loadout data from a Google Sheet published to web as CSV, and writes lock-ins back via an Apps Script publish endpoint.

File Purpose
lessons/what-if/index.html Facilitator setup instructions — how to publish the spreadsheet as CSV and where to paste the URL
lessons/what-if-analysis.html The student-facing lesson that reads the published CSV at run time
Facilitator action The spreadsheet must be File → Share → Publish to web → CSV before the student page can read it. Paste the CSV URL into config.js under whatIfSheetCsvUrl. The student page caches the CSV — if you update the sheet, give it a minute to propagate, or have students hard-refresh.
05 Central config — one file for every endpoint. Edit here, not elsewhere

config.js is the only file where endpoint URLs live. Lesson pages, dashboards, and analysis pages all import their URLs from here.

File What it defines
config.js whatIfSheetCsvUrl (per-site overrides supported) · whatIfLockinsCsvUrl · whatIfPublishEndpoint · per-site Apps Script web app URLs for the dashboard / leaderboard.
Facilitator action Whenever a sheet changes — new URL, new tab, new state added, new Apps Script deployment — this is the only file to edit. All the lesson pages and dashboards read from here. Update once, redeploy to Vercel, every page picks up the new endpoint.

If a spreadsheet integration breaks, start at config.js — the endpoint URL is almost always the cause. For Apps Script web apps specifically: editing the script does not redeploy it. Use Deploy → Manage deployments → Edit → New version → Deploy after any script change, or the old code keeps running at the old URL.
