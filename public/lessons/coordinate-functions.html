Functions & Coordinate Geometry
Teach your bot to navigate any point on the grid
Big Idea
A function is a named mini-program that bundles steps you want to reuse. Instead of rebuilding the same sequence of blocks every time, you define the logic once, give it a name, and call it with different inputs. Today you'll build moveToCoordinate(x, y) — a function that tells your bot which square to drive to on the arena grid.
Key Vocabulary
Function A named block of steps you can call over and over with different inputs.
Parameter An input slot in a function — like x or y — that changes each time you call it.
Constant (UNIT) A number that never changes. Here, 1 UNIT = 27 cm = the width of one grid square.
Absolute Value The distance from zero — always positive. |−3| = 3. Bots drive positive distances even when heading left or down.
Coordinate An ordered pair (x, y) that names a specific square on the grid. x moves left/right; y moves up/down.
Why Functions?

Imagine you need to send your bot to five different squares in a match. Without a function, you'd copy the same 10+ blocks five times. One mistake anywhere breaks everything.

With a function, you write the logic once. To send the bot to square (3, 2) you just write:

call moveTo(3, 2)

Change the numbers and the bot goes somewhere else — same logic, zero rewriting. This is exactly how professional robotics software works.

The Grid

Your arena is a coordinate grid. The bot starts at (0, 0). Each square is 27 cm × 27 cm — that's your UNIT. Positive x goes right, negative x goes left. Positive y goes forward, negative y goes backward.

The bot starts at (0, 0). Every square it moves right adds 1 to x. Every square forward adds 1 to y.

Quick Check

If your bot is at (0, 0) and you call moveTo(3, 2), which direction does the bot move first?

Build moveTo(x, y)
Steps 8–25: Define the function, then wire up buttons
Part A — Create the Function
  • 8
    Click Advanced in the toolbox, then select Functions. Click Make a Function.
  • 9
    Name the function moveTo. Add two number inputs and rename them x and y. Press Done.
    These two parameters are the coordinate the bot should drive to. Every time you call moveTo, you plug in different numbers.
Part B — Move in the X Direction First

The bot always handles x (left/right) before y (forward/back). It needs to decide which way to turn based on whether x is positive or negative.

  • 10
    Inside moveTo, add an if/else block from the Logic section.
  • 11
    Set the condition to x < 0. If x is negative, the bot needs to face left.
  • 12
    In the then branch: add set car turn left at place for angle 90 (Cutebot Pro section).
  • 13
    In the else branch: add set car turn right at place for angle 90.
  • 14
    Below the if/else, add a go forward block (PID Control section). For the distance, use:
    go forward ▾ absolute of x × UNIT cm ▾
    Why absolute value?
    Distance is always positive — you can't drive −3 cm. If x = −2, |−2| = 2, so the bot drives 2 squares. The direction was already set by the turn, so the forward distance is just the magnitude.
Part C — Move in the Y Direction Second

After finishing the x move, the bot now needs to face the right direction for y. The turn depends on both x and y: if the bot already turned right for x (x > 0), it needs to turn left to face forward. If it turned left for x (x < 0), it needs to turn right to face forward.

  • 15
    Add another if/else block below the go forward block.
  • 16
    Set the condition to x < 0. If x was negative (bot turned left), it now turns right to face forward for the y move.
  • 17
    In the then branch: set car turn right at place for angle 90.
  • 18
    In the else branch: set car turn left at place for angle 90. (If x was positive, the bot turned right to start, so it now turns left to face forward.)
  • 19
    Add a final go forward block with:
    go forward ▾ absolute of y × UNIT cm ▾

Bot Navigation Challenges
Use your function to navigate multi-point routes

For each challenge, place your bot at (0, 0) and program the correct button. Each call to moveTo moves the bot from its current position — so the coordinates are relative to the last stop.

Button A
Single Move
Drive the bot from (0, 0) to square (3, 2). One call, one destination.
(0, 0) → (3, 2)
on button A ▾ pressed
call moveTo 3 2
The bot turns right 3 squares, then forward 2 squares. Total distance: 3 × 27 + 2 × 27 = 135 cm.
Button B
Two-Stop Route
Drive from (0, 0) → (3, 2) → (5, 4). Two calls in sequence.
(0, 0) → (3, 2) → (5, 4)
on button B ▾ pressed
call moveTo 3 2
call moveTo 2 2
The second call uses (2, 2) — not (5, 4) — because the bot is already at (3, 2). You're telling it how far to move from where it is now.
Why (2, 2) not (5, 4)?
The function moves the bot by the number you pass in, starting from its current position. If the bot is at (3, 2) and you want it at (5, 4), it needs to move 2 more squares right and 2 more squares forward. So you pass (2, 2).
Button A+B
Three-Stop Route
Drive from (0, 0) → (3, 2) → (5, 4) → (2, 4). Three calls in sequence.
(0, 0) → (3, 2) → (5, 4) → (2, 4)
Work out the third move
Bot is at (5, 4). Target is (2, 4). Difference: x = 2 − 5 = −3, y = 4 − 4 = 0. So the third call is moveTo(−3, 0). Negative x = turn left.
Math Connection: Relative vs. Absolute Coordinates
Your function uses relative coordinates — each call describes how far to move from the current position, not from the origin. To find the input for a move, subtract the current position from the target:

Δx = x_target − x_current    Δy = y_target − y_current

If you were building a GPS-style function that always started from (0, 0), you'd use absolute coordinates and pass the target directly. Both approaches are valid — they just require different logic inside the function.

Extension Challenge
